# v0.4.0 — AoE2 ladder: scope & design notes

Working document for the v0.4.0 milestone rework. Lives on the planning
branch; content will be folded into issues, ROADMAP and `docs/MODS/ladder/`
once agreed. Nothing here changes existing code or docs.

## 1. Objective

Ship the first real game + mod on Kingdoms: an **AoE2 ladder**, migrated
from the JeanJack project ("refait en mieux", not literally iso — same
player experience, better architecture).

## 2. Architecture (decided — ADR-0020)

Three process families: `bot-discord`, `svc-core`, `ext-<provider>`
(`ext-librematch`, `ext-aoe2lobby`). Games and mods are *modules* in
`svc-core` (`games/aoe2`, `mods/ladder`), with a surface in `bot-discord`.
Providers are dedicated processes owning their secrets, rate limits and
caching.

## 3. Scope — what v0.4.0 must contain

From the existing milestone 3, requalified for AoE2-ladder-first:

1. **Process split scaffolding** (new): RPC contracts bot↔core and
   core↔providers, per-process deployment in kingdoms-infra.
2. **AoE2 game module + providers** (kingdoms-services#27, #8):
   `ext-librematch` and `ext-aoe2lobby` adapters — match data, profile
   validation.
3. **Registration & profile validation** (kingdoms-services#14, #25):
   DM enrollment flow; validating the player's AoE2 profile (identity
   binding to the external account, via provider data).
4. **Seasons — seasonal mod without reset** (new mechanic, extends #14/#15):
   - A **season** is a configuration entity: start, end, map pool
     rotation, and a **`reset_ratings` parameter (bool, per season)**.
   - Ladder seasons are the first use: periodic map-pool rotations, ELO
     carried over (no reset). Tournament/other mods reuse the same season
     entity later.
   - Mods declare per-season behaviour: a mod is seasonal (bound to a
     season, e.g. its map pool) vs permanent (e.g. registration/profile).
5. **Game data — generic, extensible, simple** (qualifies Epic C,
   kingdoms#112, into v0.4.0): AoE2 is the first consumer, but the model is
   game-agnostic. Three layers, declared as data, not code:
   - **Game catalog** (per game, in `svc-core`, seeded/curated via config):
     maps, civs/factions, game rules (formats, settings, team sizes),
     versioned. AoE2 data (map list, civ list, RM settings) imported once,
     then maintainable without code.
   - **Season map pool** (per season, per mod): a *selection* into the
     catalog — which maps/civs are in play this rotation, with pick/ban/
     draft parameters. This is what makes the ladder "seasonal without
     reset": the rotation changes, the ratings don't.
   - **Mod rules**: per-mod configuration referencing catalog entries
     (e.g. ladder: which maps are challengeable; tournament: mappool draft).
   Design constraints:
   - **Discord-first admin surface** (hard requirement): admins manage
     everything from Discord — create a map that doesn't exist yet in the
     DB, create/edit map pools, optionally link pools to a map pack.
     Admin commands (extending the admin mod, kingdoms-services#21):
     `/admin gamedata ...` (game, map, civ, rule CRUD), `/admin mappool
     ...` (create/edit pools, add/remove maps, link to a pack). No dev
     action required for any of these — limiting dev involvement is an
     explicit goal; Discord is the admins' only tool.
   - **editable config files** remain the seeding/import path (YAML per
     ADR-0008 conventions) for bulk initial data; after seeding, Discord
     commands are the management surface. Both paths write the same
     versioned data through `svc-core` — never direct DB edits;
   - manipulation by non-devs is a hard requirement, and the YAML
     seeding files follow ADR-0008 conventions;
   - references are stable IDs (map/civ/rule keys), so rotating a pool
     or adding a civ never breaks seasons in progress;
   - generic core (`games/<game>/data/` contract), AoE2 as the first
     implementation.
   - **Map packs** (new entity): a named bundle of maps usable as a
     building block for pools (e.g. a themed pack referenced by several
     pools/seasons). Pools may reference packs or individual maps.
6. **Ladder mod** (kingdoms-services#15), migrated from JeanJack:
   - **Queue matchmaking**: players join a queue; a match is created when
     two players of close enough level are waiting, or after they have
     waited long enough (widening threshold over time).
   - **Direct challenge**: challenge a specific player on a specific map,
     handled via DM (challenge, accept/decline, confirmation).
   - **Match workflow via DM**: match creation, map announcement,
     result reporting/confirmation, dispute window.
   - **Channels**: match-feed channel, rankings/standings channel (already
     in the ladder env doc), season announcements.
7. **Channel access policies** (kingdoms-services#57) — prerequisite for
   the ladder channels.
8. **Admin game-data surface** (extends kingdoms-services#21): the
   admin mod must expose game-data & map-pool management commands on
   Discord (see design constraints in point 5). Included in v0.4.0
   because the ladder's seasonal rotations depend on it.

Deferred from milestone 3 (to be re-triaged): clans mod (#19), tournament
80% (#120) — v0.4.0 focuses on the ladder vertical slice. To confirm with
the developer.

## 4. Open questions

- RPC transport choice (library/serialization) — developer's call.
- Match result source of truth: resolved by the reference §5.2 — both
  paths exist; reliable provider result + `auto_confirm_system_report`
  → direct COMPLETED, otherwise manual confirmation; conflicts alert
  admins (never a silent correction).
- Queue parameters: port JeanJack values from the reference §2
  defaults (base threshold 60, +20 every 15 s, cap 400).
- Map pool size and rotation cadence for AoE2 seasons — admin-managed
  via the Discord surface; initial AoE2 pool seeded at rollout.
- AoE2 civ/map metadata: manual curation vs aoe2lobby/LibreMatch
  reference data — to resolve at provider implementation. Drafts
  (pick/ban) are NOT in v0.4.0: the ladder uses pool selection +
  weighted pick per reference §4; full drafts lean Epic C/tournament.
- Both `ext-librematch` and `ext-aoe2lobby` are in scope (§5.2 point 4);
  AoE2 civs/factions stay opaque gateway-supplied data (reference §6) —
  the AoE2 provider supplies labels; the game catalog holds the
  curated civ list for admin editing.

## 5. JeanJack migration inputs

The JeanJack functionality report is archived as a living reference:
[ladder-1v1-jeanjack-v2.md](reference/ladder-1v1-jeanjack-v2.md).
It is the **functional source of truth** for the ladder mod (rules,
state machine, data model, admin surface, acceptance criteria — sections
§2–§9 of the reference).

### 5.1 Mapping to Kingdoms

The reference assumes ports (`PlatformGateway`, `GameGateway`, message
registry) that map onto Kingdoms seams, with the ADR-0020 process split:

| Reference concept | Kingdoms counterpart |
|---|---|
| `PlatformGateway` | existing `IPlatform` / DiscordPlatform seam (ADR-0016), extended with: identity resolution, message registry, named surfaces, permission queries |
| `GameGateway` | new `IGameProvider`-family seam (kingdoms-services#27, ADR-0011), implemented by `ext-librematch` / `ext-aoe2lobby` processes (ADR-0020) |
| Message registry `(platform, key, entity_id)` | to add as a core service (bot-discord side), per §2.3 of the reference |
| Mod core (`rules, rating, matchmaking, maps, persistence`) | `mods/ladder` module **in svc-core** |
| Platform adapter (views/modals/intents) | ladder surface **in bot-discord** |
| Game adapter | `games/aoe2` module in svc-core + provider processes |
| Notification intents (§7.2) | map onto the i18n + delivery seams (kingdoms-services#17, #56) |

The reference's non-negotiables (no platform/game IDs in mod
collections, idempotent transitions, declared capabilities with clean
degradation, mock-based acceptance) are adopted as-is — they match
ADR-0011/0012/0019 rules already in force.

### 5.2 Decisions (confirmed 2026-09-28)

1. **Pluggable rating systems** (developer decision): `rating_system`
   is an admin-selectable setting per ladder. v0.4.0 ships two
   implementations — **Elo** (the reference §3 rules, verbatim: K
   évolutif, bornes, floor, idempotent single application,
   rating_history as source of truth) and **Glicko-2** (Epic D's system:
   rating + deviation + volatility, RD-based K, inactivity decay via
   RD growth, provisional detection via RD threshold instead of
   match count). Design: a `RatingSystem` seam in `mods/ladder` —
   `apply_result(players, result) -> rating_deltas`, `initial_rating()`,
   `expected_outcome()` — registered by key. The invariants (single
   application, rating_history source of truth, correction with
   compensation) are rating-system-agnostic and stay in the core.
   Glicko-2 stores per-player extra state (RD, volatility) on the
   ladder's `players` collection as a system-owned block. Later systems
   (TrueSkill-style, OpenSkill) plug in without touching the state
   machine.
2. **Seasons** — confirmed: `active_map_pool_id` + `map_pool_history`
   on the ladder, wrapped by the season config (start/end,
   `reset_ratings` per season, false for AoE2 ladder). Season
   activation = transactional pool switch per reference §4.
3. **Registration/profile binding** — confirmed: register mod (#14/#25)
   + provider validation, consumed via the game-provider seam's
   identity resolution.
4. **Providers are in v0.4.0 scope**: `ext-librematch` and
   `ext-aoe2lobby` are developed in this milestone (ADR-0020
   processes). Realtime events and auto-reported results land if the
   providers expose them — the core must pass acceptance without them
   (reference criterion 1).
5. **Rating lives on the ladder's `players` collection** — confirmed;
   `docs/MODS/ladder/` is rewritten from the reference.

### 5.3 Algorithm choices (delegated to the implementer — decided)

- **Matchmaking**: keep the reference's maximum matching semantics
  (never leave a pairable player alone when a complete matching
  exists). Implementation: general-graph maximum matching (the queue
  is not bipartite — any two compatible players can pair), Edmonds'
  blossom algorithm; queue sizes are small (< 100), so an exact
  optimal matching with the reference's tie-break ordering
  `(min(pair_count), sum pair_count, |Δrating|)` is cheap enough — no
  greedy compromise needed.
- **Map pick**: weighted random with fav-boosted weights (reference
  §4) — kept as-is; simple and explainable.
- **Rating**: Elo per reference §3; Glicko-2 per Glickman's 2013 paper
  (step-by-step with tau, standard constants: rating ~1000-scale,
   RD 350, volatility 0.06).
